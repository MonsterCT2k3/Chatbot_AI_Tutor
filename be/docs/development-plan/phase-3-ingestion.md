## Phase 3 — Ingestion pipeline (phase nặng nhất, tách test riêng trước khi nối vào chat)

**Quyết định kiến trúc đã chốt (khác với bản guide gốc):**
- **PPTX luôn được convert sang PDF trước** (LibreOffice headless), sau đó dùng **chung 1 pipeline PDF** cho cả PDF gốc lẫn PPTX-đã-convert. Bỏ `python-pptx` khỏi dependency thật (chỉ giữ lại để tạo file test .pptx ở bước 3.5).
- File PDF convert ra từ PPTX **được lưu lại trên R2** (cột `documents.converted_pdf_key`, migration `576b20e69d44` đã chạy) — không chỉ dùng tạm.
- **Text extraction hỗ trợ 3 chế độ song song, chọn được, lưu lại đã dùng chế độ nào:**
  - `pypdf` — nhanh, miễn phí, đủ dùng cho phần text thuần.
  - `mistral_ocr` — dùng model `mistral-ocr-latest` cho **toàn bộ** trang, xử lý được cả nội dung trong hình ảnh/diagram. Chi phí cao nhất trong 3 mode vì OCR mọi trang.
  - `hybrid` — `pypdf` làm baseline cho mọi trang, tự động phát hiện trang nào có ảnh nhúng rồi chỉ gọi Mistral OCR cho đúng những trang đó. Rẻ hơn `mistral_ocr` nếu tài liệu ít ảnh — **lưu ý trung thực:** với `b3.pdf` (85% trang có ảnh) thì `hybrid` gần như không rẻ hơn `mistral_ocr` bao nhiêu.
  - Chọn chế độ qua field `extraction_mode` khi upload (`POST /api/documents`, mặc định `pypdf` vì miễn phí), lưu vào `documents.metadata.extraction_mode` (dùng cột `metadata` JSONB có sẵn, không cần thêm cột DB mới).
- **`mistral_ocr` (và `hybrid`) là pipeline 2 giai đoạn, không phải 1 lệnh gọi API đơn giản** — phát hiện quan trọng sau khi đọc lại code cũ (`be/pdf_extract/`, pipeline Mistral OCR user đã tự xây và dùng thấy ổn trước đây):
  1. **Giai đoạn 1 — OCR:** `mistral-ocr-latest` trả về `page.markdown`, nhưng ảnh/diagram trong đó chỉ là **tag placeholder** (`![img-0.jpeg](img-0.jpeg)`), KHÔNG có mô tả nội dung. Nếu dùng thẳng `page.markdown` như bản kế hoạch trước, phần ảnh coi như vô dụng cho RAG (embedding của 1 cái tag ảnh không mang nghĩa gì).
  2. **Giai đoạn 2 — Vision description:** từng ảnh trích được (`page.images[]`, base64) được gửi riêng qua model vision `pixtral-12b-2409` với 1 prompt có cấu trúc (phân biệt: biểu đồ/sơ đồ → trích cấu trúc + số liệu; ảnh chữ/code → OCR lại 100%; ảnh trang trí/logo → bỏ qua ngắn gọn). Mô tả trả về **thay thế** tag ảnh trong markdown.
  - Đã kiểm chứng chất lượng thật: mô tả 1 sơ đồ kiến trúc (trang 19, `b3.pdf`) ra đúng cấu trúc 5 bước, tên từng box, màu sắc, đúng với nội dung — chất lượng đủ tốt để tái sử dụng gần như nguyên bản prompt.
  - **Không cần** bước upload file lên Mistral Storage riêng như code cũ (`client.files.upload` + `get_signed_url`) — mình đã có sẵn presigned URL từ R2 (Phase 2), truyền thẳng vào `document_url` là đủ, đỡ 1 bước.
  - **Áp dụng retry với exponential backoff** cho cả 2 lệnh gọi API (OCR + vision) — API bên ngoài có thể lỗi mạng/SSL tạm thời, code cũ đã có cơ chế này (`retry_api_call`) và hoạt động tốt, tái sử dụng lại pattern.
- **KHÔNG render ảnh PNG từng trang nữa (đã bỏ so với bản kế hoạch trước)** — quyết định lại: viewer sẽ hiển thị **thẳng file PDF gốc** (dùng `PDF.js`/`react-pdf` ở frontend) thay vì ảnh tĩnh từng trang. Lý do: ảnh tĩnh không cho copy/select text được, còn PDF.js vừa giữ được text layer thật (copy được) vừa vẫn hỗ trợ nhảy tới trang cụ thể + vẽ overlay highlight theo toạ độ (dùng `document_chunks.bbox` sau này) — được cả 2 thứ, không đánh đổi. Xem chi tiết bàn luận ở [Phase 4](phase-4-viewer-api.md). Hệ quả: `document_pages.thumbnail_key` không còn được ingestion điền vào nữa (cột vẫn còn trong schema, để `null`, không cần migration xoá).

**Chi tiết kỹ thuật Mistral OCR (đã tra cứu docs thật + đối chiếu code cũ đã chạy thật, không đoán):**
- Model OCR: `mistral-ocr-latest`. Model vision (mô tả ảnh): `pixtral-12b-2409`. Cả 2 gọi qua SDK chính thức `mistralai` (`pip install mistralai`, cần thêm vào `requirements.txt`).
- Input OCR là `document_url` — **truyền thẳng presigned URL từ R2** (dùng lại `storage_service.get_presigned_url()` đã build ở Phase 2).
- Cần truyền `include_image_base64=True` khi gọi `client.ocr.process(...)` để lấy được ảnh nhúng dạng base64 trong `page.images[]` (nếu không có flag này sẽ không có ảnh để phân tích ở giai đoạn 2).
- Tham số `pages` (optional) — nhận list số trang (0-indexed, VD `[0, 2, 4]`) để chỉ OCR đúng những trang đó trong **1 lần gọi API** — chính là cơ chế `hybrid` mode dùng để tiết kiệm chi phí.
- **Giá OCR: ~$4/1000 trang** (rẻ hơn 50% nếu dùng Batch API — chưa cần quan tâm ở MVP). Vision (Pixtral) tính riêng theo số ảnh thực tế gửi đi, không phải theo số trang.

**Hạ tầng cần có trước khi code (đã kiểm tra thật, không giả định):**
- ✅ **LibreOffice headless** — đã cài xong (`LibreOffice 26.2.4.2`), verify qua `soffice --version` và test convert thật ở bước 3.5.
- `tiktoken` — đã thêm vào `requirements.txt` và cài xong, dùng đếm token khi chunk.
- `mistralai` — đã thêm vào `requirements.txt` và cài xong. **Lưu ý:** bản 2.9.1 đã cài thực tế import là `from mistralai.client import Mistral`, KHÔNG phải `from mistralai import Mistral` như docs chính thức ghi (top-level `mistralai/__init__.py` không export lại) — đã verify trực tiếp, dùng đúng đường dẫn này khi code.
- `MISTRAL_API_KEY` đã có sẵn trong `.env` từ trước (key thật, dùng được ngay) — cũng chính là key code cũ (`be/pdf_extract/`) đã dùng.
- **Tài nguyên test cho các bước có tốn phí API (OCR/vision):** dùng `app/data/slide-test/*.pdf` (bản rút gọn ~10 trang mỗi file, cắt từ file gốc) thay vì file đầy đủ trong `app/data/slide/` — nhanh và rẻ hơn khi test lặp lại nhiều lần. `b3-test.pdf` có 10/10 trang đều có ảnh — dùng để test kỹ nhất phần vision/OCR.

**Bằng chứng thực tế đã kiểm chứng trên 3 file PDF thật (`b1.pdf`, `b3.pdf`, `b5.pdf`, tổng 200 trang):**
- 0/200 trang bị thiếu text (không phải PDF dạng ảnh/scan — `pypdf` đọc được text thật ở mọi trang).
- Có lỗi nhỏ: `pypdf` đôi khi mất dấu cách giữa các đoạn text liền kề khác định dạng (VD "KiếnTrúcAgent" thay vì "Kiến Trúc Agent") — chấp nhận được, embedding vẫn hiểu đúng ý.
- `b3.pdf`: **66/78 trang (85%) có ít nhất 1 ảnh nhúng** — đây là lý do chính cần có lựa chọn OCR, không phải vì lo PDF dạng scan.
- Đã xem output thật từ pipeline cũ (`be/pdf_extract/output_ocr/b3/b3_full_rag_ready.md`) — mô tả ảnh/diagram chất lượng tốt, đúng nội dung, súc tích, phù hợp cho RAG.
