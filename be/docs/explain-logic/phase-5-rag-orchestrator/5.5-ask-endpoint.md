## 5.5 — Endpoint tạm `POST /api/documents/{document_id}/ask`

**File:** [`app/routers/documents.py`](../../../app/routers/documents.py), [`app/schemas/rag.py`](../../../app/schemas/rag.py) (mới), [`app/services/document_service.py`](../../../app/services/document_service.py) (thêm `ensure_document_ready`)

### Code

```python
# schemas/rag.py
class AskRequest(BaseModel):
    question: str = Field(min_length=1)


class CitationResponse(BaseModel):
    page_number: int
    chunk_id: uuid.UUID
    snippet: str


class AskResponse(BaseModel):
    answer: str
    citations: list[CitationResponse]
```

```python
# document_service.py
def ensure_document_ready(document: Document) -> None:
    # Chunks/embeddings only exist once ingestion has fully finished — asking
    # a question before that would just search against an empty/partial set.
    if document.status != "ready":
        raise DocumentNotReadyError()
```

```python
# routers/documents.py
@router.post("/{document_id}/ask", response_model=AskResponse)
async def ask_document(
    document_id: uuid.UUID,
    payload: AskRequest,
    current_user: User = Depends(get_current_user),
    db: AsyncSession = Depends(get_db),
):
    try:
        document = await get_owned_document(db, document_id, current_user.id)
        ensure_document_ready(document)
    except DocumentNotFoundError:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail={"code": "DOCUMENT_NOT_FOUND", "message": "Document not found"},
        )
    except DocumentNotReadyError:
        raise HTTPException(
            status_code=status.HTTP_409_CONFLICT,
            detail={"code": "DOCUMENT_NOT_READY", "message": "The document isn't fully ingested yet"},
        )

    result = await ask(db, document_id, payload.question)
    citations = parse_citations(result.answer, result.chunks)

    return AskResponse(
        answer=result.answer,
        citations=[
            CitationResponse(page_number=c.page_number, chunk_id=c.chunk_id, snippet=c.snippet) for c in citations
        ],
    )
```

### Nó làm gì (ý nghĩa)

Nối toàn bộ 5.1-5.4 (retrieval → prompt → LLM → citation) thành 1 API thật gọi được qua HTTP — lần đầu tiên trong Phase 5, người dùng (hoặc frontend) có thể thật sự POST 1 câu hỏi và nhận về câu trả lời + trích dẫn, không cần chạy script Python nữa. Đây là endpoint TẠM (xem ghi chú đầu file kế hoạch Phase 5) — sẽ bị thay bằng `POST /api/sessions/{id}/messages` thật ở Phase 6, khi đó chỉ đổi LỚP GỌI VÀO, không đổi logic RAG bên trong.

### Luồng chạy chi tiết

Lấy đúng ví dụ đã test thật: `document_id` của 1 document đã `ready`, `payload.question = "Ai là giảng viên hướng dẫn khóa học AI in Action Day 1?"`.

1. **FastAPI validate `payload` trước khi handler chạy** — `AskRequest` yêu cầu `question` có `min_length=1`; nếu request gửi `{"question": ""}`, FastAPI tự trả `422` NGAY, hàm `ask_document` không hề được gọi tới (đã kiểm chứng thật — xem phần Test).
2. **`get_owned_document(db, document_id, current_user.id)`** — tra `document_id` VÀ đối chiếu đúng `user_id` của người gọi trong 1 câu query — nếu không tìm thấy (document không tồn tại, HOẶC tồn tại nhưng thuộc user khác), raise `DocumentNotFoundError`, nhảy thẳng xuống khối `except` đầu tiên → `404`.
3. **`ensure_document_ready(document)`** — kiểm tra `document.status`. Với ví dụ thật: `status == "ready"` nên hàm này chạy xong không làm gì cả (không raise), luồng tiếp tục xuống dưới. Nếu `status` là `"pending"`/`"parsing"`/`"embedding"`/`"failed"` (document ở ví dụ CHƯA ingest ở 1 case test khác), raise `DocumentNotReadyError` → nhảy xuống khối `except` thứ hai → `409`.
4. **`await ask(db, document_id, payload.question)`** (5.3) — bên trong: embed câu hỏi → `similarity_search` (5.1) tìm ra 6 chunk liên quan nhất (chunk trang 1 xếp đầu) → `build_prompt` (5.2) dựng `messages` → gọi OpenAI thật → nhận về `AnswerResult(answer="Giảng viên hướng dẫn... [Trang 1]", chunks=[...6 chunk...])`.
5. **`parse_citations(result.answer, result.chunks)`** (5.4) — quét `answer` tìm tag `[Trang 1]`, khớp với chunk trang 1 trong `result.chunks` (có thật, được kiểm chứng chứ không tin mù) → trả về `[Citation(page_number=1, chunk_id=<uuid thật>, snippet="AI IN ACTION...")]`.
6. **Dựng `AskResponse`** — chuyển từng `Citation` (dataclass nội bộ của `rag_service`) thành `CitationResponse` (Pydantic schema, dùng để serialize ra JSON) — 2 kiểu dữ liệu tách biệt có chủ đích (xem mục "Tại sao" bên dưới).
7. **Response middleware** (đã có từ Phase 1) tự bọc `AskResponse` vào envelope chuẩn `{success, message, data, error, requestId}` trước khi trả về client — response cuối cùng người dùng thấy có `data.answer` và `data.citations`.

### Tại sao code theo cách này

1. **Vì sao thêm `ensure_document_ready` thay vì để `ask()` (5.3) tự nhiên chạy trên document chưa có chunk?** — nếu không chặn sớm, `similarity_search` sẽ trả về `[]` (document chưa ingest thì chưa có `document_chunks` nào), `build_prompt` sẽ dựng context rỗng, và hệ thống vẫn TỐN 1 lệnh gọi OpenAI thật (embed câu hỏi + chat completion) chỉ để nhận lại câu "không tìm thấy trong tài liệu" — vừa tốn tiền, vừa dễ gây hiểu lầm cho người dùng (tưởng tài liệu thật sự không có nội dung đó, thay vì hiểu đúng là "tài liệu chưa xử lý xong"). Chặn sớm bằng `409` rõ ràng hơn nhiều.
2. **Vì sao `CitationResponse` (Pydantic, trong `schemas/rag.py`) là 1 class RIÊNG với `Citation` (dataclass, trong `rag_service.py`) dù 2 class có field giống hệt nhau?** — đây là ranh giới kiến trúc đã áp dụng xuyên suốt dự án: `rag_service.py` (tầng service/logic nghiệp vụ) không nên biết gì về Pydantic/FastAPI (tầng HTTP) — `Citation` là kiểu dữ liệu nội bộ, thuần Python, dùng được ở bất kỳ ngữ cảnh nào (kể cả khi KHÔNG có HTTP, ví dụ gọi trực tiếp từ script hay từ 1 worker khác sau này). `CitationResponse` chỉ tồn tại để phục vụ việc serialize JSON cho đúng 1 endpoint HTTP cụ thể.
3. **Vì sao endpoint là `POST /{document_id}/ask` gắn trong `documents.py` (router đã có), không tạo router riêng?** — đúng quyết định kiến trúc đã chốt ở đầu Phase 5: đây là endpoint TẠM, cố tình KHÔNG đụng tới `chat_sessions`, gắn thẳng vào tài nguyên `document` cho gọn — tạo hẳn 1 router mới cho 1 endpoint tạm sẽ là over-engineering không cần thiết.
4. **Vì sao không giới hạn độ dài tối đa của `question` (chỉ có `min_length=1`, không có `max_length`)?** — chưa cần thiết ở bước này: giới hạn chi phí/lạm dụng (câu hỏi quá dài, quá nhiều request...) thuộc đúng phạm vi của Phase 5.6 (guardrail) đã lên kế hoạch riêng — thêm giới hạn tùy tiện ở đây mà không có cơ sở (VD giới hạn bao nhiêu ký tự là hợp lý?) sẽ là đoán mò, tốt hơn nên làm có chủ đích ở đúng phase của nó.

### Test đã chạy (bằng chứng thật)

Test qua HTTP thật (`httpx.AsyncClient` + `ASGITransport`), đăng ký user thật, upload + ingest thật `b1-test.pdf`:

| Case | Kết quả |
|---|---|
| Hỏi trên document CHƯA ingest (`status='pending'`) | `409 DOCUMENT_NOT_READY` |
| Hỏi trên document đã `ready`, câu hỏi thật ("Ai là giảng viên...") | `200`, `answer` đúng nội dung kèm `[Trang 1]`, `citations` có 1 phần tử đúng `page_number=1` + `chunk_id`/`snippet` thật |
| Câu hỏi rỗng (`question=""`) | `422`, bị chặn ở tầng validate của Pydantic, KHÔNG chạy vào handler (không tốn API call) |
| `document_id` ngẫu nhiên không tồn tại | `404 DOCUMENT_NOT_FOUND` |
| Không có token xác thực | `401` |

### Bước này kết nối với các bước sau như thế nào

- **5.6 (test edge case)** sẽ dùng chính endpoint này để test case "hỏi ngoài phạm vi tài liệu" + "document không có chunk nào dù đã `ready`" qua HTTP thật.
- **Phase 6** thay endpoint tạm này bằng `POST /api/sessions/{id}/messages` — logic bên trong (`ask` + `parse_citations`) giữ nguyên, chỉ đổi cách lấy `document_id` (từ `session.document_id` thay vì thẳng từ URL) và thêm việc lưu `chat_messages`.
- **Phase 7 (streaming)** sẽ đổi cách gọi `ask()` ở bước 4 thành generator stream, nhưng bước 2-3 (kiểm tra document) và bước 5 (`parse_citations`) không đổi.
