## 5.3 — `ask`: orchestrate toàn bộ RAG (chưa streaming)

**File:** [`app/services/rag_service.py`](../../app/services/rag_service.py), [`app/services/ingestion_service.py`](../../app/services/ingestion_service.py) (đổi tên `_retry_async` → `retry_async`)

### Code

```python
_openai_client = AsyncOpenAI(api_key=settings.OPENAI_API_KEY)


@dataclass
class AnswerResult:
    answer: str
    chunks: list[DocumentChunk]


async def ask(db: AsyncSession, document_id: uuid.UUID, question: str) -> AnswerResult:
    query_embedding = (await embed_chunks([question]))[0]
    chunks = await similarity_search(db, document_id, query_embedding)
    messages = build_prompt(chunks, question)

    async def _call():
        return await _openai_client.chat.completions.create(model=settings.CHAT_MODEL, messages=messages)

    response = await retry_async(_call)
    answer = response.choices[0].message.content
    return AnswerResult(answer=answer, chunks=chunks)
```

### Nó làm gì (ý nghĩa)

Ghép 5.1 + 5.2 lại thành 1 luồng RAG hoàn chỉnh, thật sự chạy được: nhận 1 câu hỏi thô của người dùng → trả về 1 câu trả lời thật từ LLM, có trích dẫn. Đây là hàm "mặt tiền" (entry point) mà mọi endpoint (5.5 và sau này Phase 6/7) sẽ gọi.

### Tại sao code theo cách này

1. **Vì sao dùng lại `ingestion_service.embed_chunks([question])` thay vì viết 1 hàm `embed_query` riêng?** — về bản chất kỹ thuật, "embed 1 câu hỏi" và "embed 1 chunk văn bản" là CÙNG 1 việc: gọi OpenAI embeddings với `input` là 1 list string, lấy vector đầu tiên. Viết thêm 1 hàm chỉ để đổi tên gọi là trùng lặp không cần thiết (vi phạm nguyên tắc không tạo abstraction thừa) — `embed_chunks([question])[0]` diễn đạt đúng ý và không cần code mới.
2. **Vì sao đổi tên `_retry_async` → `retry_async` (bỏ dấu gạch dưới đầu) thay vì cứ import thẳng tên có gạch dưới từ `ingestion_service`?** — dấu gạch dưới đầu tên trong Python là quy ước báo hiệu "riêng tư, chỉ dùng nội bộ module này" — khi `rag_service.py` cũng cần dùng hàm này, nó không còn là chi tiết riêng của `ingestion_service` nữa mà là 1 tiện ích dùng chung giữa 2 service. Đổi tên phản ánh đúng thực tế mới, tránh tín hiệu sai lệch cho người đọc code sau này.
3. **Vì sao `AnswerResult` giữ lại cả `chunks` đã dùng, không chỉ trả về `answer` (string)?** — bước 5.4 (`parse_citations`) cần biết CHÍNH XÁC những chunk nào đã đưa vào context để khớp trích dẫn `[Trang X]` với đúng `chunk_id`/`snippet` — nếu `ask()` chỉ trả về text, nơi gọi phải chạy lại `similarity_search` lần 2 (tốn thêm 1 câu query DB + có rủi ro kết quả khác đi nếu dữ liệu đổi giữa 2 lần gọi). Trả kèm `chunks` tránh hoàn toàn vấn đề này.
4. **Vì sao tạo `_openai_client` mới trong `rag_service.py` thay vì tái sử dụng `_openai_client` đã có sẵn trong `ingestion_service.py`?** — giữ đúng khuôn mẫu đã có trong dự án: mỗi service module tự khởi tạo client riêng cho các API bên ngoài nó cần dùng (`ingestion_service.py` cũng tự có cả `_openai_client` lẫn `_mistral_client`) — tránh việc 1 module phải "với tay" vào biến riêng tư của module khác, giữ ranh giới module rõ ràng. Chi phí thêm 1 client instance gần như bằng 0.
5. **Vì sao bọc lệnh gọi Chat Completions bằng `retry_async` giống mọi lệnh gọi API ngoài khác trong dự án?** — tính nhất quán: `_describe_image_pixtral`, `extract_text_mistral_ocr`, `embed_chunks` (Phase 3) đều đã có retry với exponential backoff cho lỗi mạng tạm thời — lệnh gọi Chat Completions ở đây cũng là 1 API bên ngoài, không có lý do để nó là ngoại lệ duy nhất không có retry.

### Bước này kết nối với các bước sau như thế nào

- **5.4 (`parse_citations`)** nhận `result.answer` + `result.chunks` từ hàm này để khớp trích dẫn `[Trang X]` với `chunk_id` thật.
- **5.5 (endpoint tạm `POST /api/documents/{document_id}/ask`)** gọi thẳng hàm này để có câu trả lời thật trả về qua HTTP.
- **Phase 7 (streaming)** sau này sẽ đổi phần gọi Chat Completions ở đây từ `stream=False` sang generator `stream=True` — nhưng phần 5.1 (retrieval) + 5.2 (build prompt) giữ nguyên không đổi.
