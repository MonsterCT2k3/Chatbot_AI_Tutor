## 3.5 — `convert_pptx_to_pdf`: convert PPTX sang PDF bằng LibreOffice

**File:** [`app/services/ingestion_service.py`](../../../app/services/ingestion_service.py)

### Code

```python
class PptxConversionError(Exception):
    pass


async def convert_pptx_to_pdf(pptx_bytes: bytes) -> bytes:
    with tempfile.TemporaryDirectory() as tmp_dir:
        tmp_path = Path(tmp_dir)
        input_path = tmp_path / "input.pptx"
        input_path.write_bytes(pptx_bytes)

        profile_dir = tmp_path / "profile"
        process = await asyncio.create_subprocess_exec(
            "soffice",
            "--headless",
            f"-env:UserInstallation=file://{profile_dir}",
            "--convert-to",
            "pdf",
            "--outdir",
            str(tmp_path),
            str(input_path),
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE,
        )
        stdout, stderr = await process.communicate()

        output_path = tmp_path / "input.pdf"
        if process.returncode != 0 or not output_path.exists():
            raise PptxConversionError((stderr or stdout).decode(errors="replace"))

        return output_path.read_bytes()
```

### Nó làm gì (ý nghĩa)

Nhận vào 1 file PPTX (dạng bytes), gọi phần mềm LibreOffice chạy ở chế độ không giao diện (`--headless`) để convert sang PDF, trả về PDF (dạng bytes). Đây là bước bắt buộc trước khi xử lý bất kỳ file PPTX nào — sau bước này, PPTX coi như "biến mất", mọi thứ phía sau (3.1/3.3/3.4) chỉ làm việc với PDF.

### Tại sao cần bước này

Đã quyết định từ đầu Phase 3: không viết pipeline xử lý PPTX riêng, mà convert hết sang PDF rồi dùng chung 1 pipeline PDF. LibreOffice là công cụ tiêu chuẩn, miễn phí, mã nguồn mở duy nhất đủ tin cậy để convert PPTX → PDF ở phía server (không có Python library thuần nào làm được việc này với chất lượng chấp nhận được — `python-pptx` chỉ đọc/ghi cấu trúc XML, không tự render ra ảnh/PDF).

### Tại sao code theo cách này (giải thích từng quyết định)

1. **Vì sao phải ghi ra file tạm (`tempfile.TemporaryDirectory`) thay vì truyền bytes trực tiếp?**
   `soffice` là 1 chương trình dòng lệnh (command-line program) — nó chỉ làm việc với file thật trên đĩa, không có cách nào truyền dữ liệu qua stdin/tham số trực tiếp cho việc convert. Bắt buộc phải: ghi bytes ra 1 file `.pptx` tạm → gọi `soffice` convert file đó → đọc file `.pdf` kết quả trở lại thành bytes. `tempfile.TemporaryDirectory()` tự động dọn dẹp toàn bộ thư mục tạm (kể cả file input lẫn output) ngay khi khối `with` kết thúc, kể cả khi có lỗi giữa chừng — không để lại rác trên đĩa server.

2. **Vì sao dùng `asyncio.create_subprocess_exec` thay vì `subprocess.run` (cách quen thuộc hơn)?**
   `subprocess.run` là hàm **blocking** — gọi nó sẽ đứng hình toàn bộ event loop trong lúc chờ LibreOffice chạy xong (LibreOffice khởi động khá chậm, vài giây), y hệt vấn đề đã gặp với `boto3` ở Phase 2. `asyncio.create_subprocess_exec` là cách "đúng chuẩn async" của Python để chạy 1 chương trình con mà không chặn luồng — khác với `boto3` (phải bọc `run_in_threadpool` vì thư viện không hỗ trợ async), ở đây `asyncio` có sẵn hỗ trợ subprocess bất đồng bộ nên dùng thẳng, không cần threadpool.

3. **Vì sao có `-env:UserInstallation=file://{profile_dir}` — dòng này làm gì?**
   Đây là điểm dễ gặp lỗi nhất khi chạy LibreOffice headless trên server thật (đã biết trước, không phải đoán): mỗi lần chạy, LibreOffice cần 1 "profile" riêng để lưu cấu hình/khoá tạm thời. Nếu 2 lần convert chạy **cùng lúc** (VD: 2 người dùng upload PPTX gần như đồng thời) mà dùng chung profile mặc định, lần thứ 2 sẽ gặp lỗi "soffice đang chạy rồi" và convert thất bại — dù file hoàn toàn hợp lệ. Cho mỗi lần gọi hàm 1 thư mục profile riêng (nằm trong chính thư mục tạm của lần gọi đó) giải quyết triệt để vấn đề này — không lo xung đột dù nhiều document ingest cùng lúc.

4. **Vì sao check cả `process.returncode != 0` LẪN `not output_path.exists()`?**
   2 cách phát hiện lỗi độc lập, phòng trường hợp 1 trong 2 không đáng tin: `returncode != 0` là cách chuẩn để biết chương trình con báo lỗi, nhưng 1 số phiên bản LibreOffice từng có trường hợp trả về `0` (coi như thành công) dù thực chất không tạo được file output (bug đã biết trong 1 số bản LibreOffice cũ). Check thêm `output_path.exists()` đảm bảo: dù `returncode` nói gì, nếu không có file PDF thật thì vẫn coi là lỗi — an toàn hơn tin tưởng 1 tín hiệu duy nhất.

5. **Vì sao tên file cố định là `input.pptx`/`input.pdf` thay vì giữ tên file gốc người dùng upload?**
   Thư mục tạm (`tempfile.TemporaryDirectory()`) đã đảm bảo mỗi lần gọi hàm có 1 thư mục riêng biệt, không đụng nhau — nên không cần tên file phải "duy nhất" theo cách nào khác. Dùng tên cố định đơn giản hoá code (biết chắc chắn LibreOffice sẽ tạo ra `input.pdf`, không cần đoán/parse tên file output dựa theo tên input gốc có thể chứa ký tự đặc biệt, dấu cách, tiếng Việt có dấu...).

### Test đã chạy (bằng chứng thật)

Convert ra PDF hợp lệ (đúng header `%PDF`), đọc lại bằng `extract_text_pypdf` (3.1) — text khớp chính xác 100% với nội dung đã đưa vào: `"Test Slide Title\nHello from pptx test fixture"` và `"Second Slide"`.

**Test lỗi:** đưa vào bytes rác (không phải PPTX thật) — xác nhận `PptxConversionError` được raise đúng, kèm message lỗi thật từ LibreOffice (`"Error: source file could not be loaded"`).

### Bước này kết nối với các bước sau như thế nào

- **3.8 (`run_ingestion`)** sẽ gọi hàm này **trước tiên** khi `document.file_type == 'pptx'` (bất kể `extraction_mode` là gì) — chuyển PPTX thành PDF ngay từ đầu, sau đó toàn bộ pipeline còn lại (3.1/3.3/3.4 tuỳ mode) chạy y hệt như đang xử lý 1 file PDF thật, không cần biết nguồn gốc là PPTX.
- PDF kết quả từ bước này cũng được **lưu lại trên R2** (`documents.converted_pdf_key`, đã quyết định từ đầu Phase 3) — không chỉ dùng tạm trong RAM rồi vứt đi.
