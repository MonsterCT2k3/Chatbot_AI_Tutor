## 3.1 — `extract_text_pypdf`: lấy text thuần từ PDF

**File:** [`app/services/ingestion_service.py`](../../app/services/ingestion_service.py)

### Code

```python
from io import BytesIO

from pypdf import PdfReader


def extract_text_pypdf(pdf_bytes: bytes) -> list[tuple[int, str]]:
    reader = PdfReader(BytesIO(pdf_bytes))
    return [(page_number, page.extract_text() or "") for page_number, page in enumerate(reader.pages, start=1)]
```

### Nó làm gì (ý nghĩa)

Nhận vào **toàn bộ nội dung file PDF dưới dạng bytes** (giống như đọc file nhị phân), trả về 1 list gồm các cặp `(số trang, nội dung text của trang đó)`. Ví dụ với file 78 trang sẽ trả về:

```python
[
    (1, "Từ Chatbot Đến Agentic Agent\nAICB-P1 · Ngày 3 · Design Pattern ReAct..."),
    (2, "? HÃY SUY NGHĨ... \"ChatGPT là chatbot hay agent?..."),
    ...
    (78, "..."),
]
```

### Tại sao cần bước này

Đây là bước đầu tiên trong việc biến 1 file PDF thô thành dữ liệu mà AI có thể "đọc" và trả lời câu hỏi được. AI (model embedding/LLM) không hiểu được file PDF — nó chỉ hiểu **text**. Muốn RAG (Retrieval-Augmented Generation — sinh câu trả lời dựa trên tài liệu tìm được) hoạt động, bắt buộc phải có bước lấy text ra trước, rồi mới chunk (bước 3.6) và embed (bước 3.7) được.

**Lưu ý quan trọng:** bước này KHÔNG liên quan gì tới việc hiển thị PDF cho người dùng xem (viewer). Viewer giờ dùng PDF.js hiển thị thẳng file gốc (đã quyết định ở [Phase 4](../../development-plan/phase-4-viewer-api.md)). `extract_text_pypdf` chỉ phục vụ 1 mục đích duy nhất: cho AI tìm kiếm/trả lời câu hỏi.

### Tại sao code theo cách này (giải thích từng quyết định)

1. **Vì sao bọc `pdf_bytes` trong `BytesIO`?**
   `PdfReader` (thư viện `pypdf`) được thiết kế để đọc từ 1 "file-like object" — tức là 1 object có các hàm `.read()`, `.seek()` giống như file thật mở bằng `open()`. Nhưng dữ liệu mình có chỉ là `bytes` thô (tải về từ R2 sẽ ở dạng bytes, không phải file trên đĩa). `BytesIO` là 1 class có sẵn của Python, biến `bytes` trong RAM thành thứ trông giống 1 file — không cần ghi ra đĩa tạm rồi đọc lại, nhanh hơn và không để lại file rác.

2. **Vì sao `enumerate(reader.pages, start=1)` mà không phải bắt đầu từ 0?**
   `reader.pages` của `pypdf` đánh số nội bộ từ 0 (theo chuẩn lập trình), nhưng trong toàn bộ hệ thống của mình, "trang 1" nghĩa là trang đầu tiên mà con người nhìn thấy (cột `document_pages.page_number` trong DB, hay khi AI trích dẫn "trang 5" thì phải khớp với trang 5 thật). Nếu để mặc định bắt đầu từ 0, trang đầu tiên sẽ bị đánh số 0 → sai lệch với số trang thật, gây lỗi khi hiển thị citation. Dùng `start=1` để số trang trong code luôn khớp với số trang con người nhìn thấy.

3. **Vì sao `page.extract_text() or ""` mà không chỉ là `page.extract_text()`?**
   Với 1 số trang đặc biệt (trang trắng hoàn toàn, hoặc lỗi parse hiếm gặp), `extract_text()` có thể trả về `None` thay vì chuỗi rỗng `""`. Nếu không xử lý, sau này khi nối text lại để chunk (bước 3.6) hoặc lưu vào cột `raw_text` (kiểu `text` trong Postgres, không nhận `None` nếu cột `not null`) sẽ bị lỗi kiểu dữ liệu. `or ""` đảm bảo luôn trả về `str`, không bao giờ là `None` — 1 dòng phòng thủ nhỏ nhưng tránh được lỗi khó debug về sau.

4. **Vì sao trả về `list[tuple]` thay vì `dict` hay 1 class riêng?**
   Ở bước này, dữ liệu đơn giản (chỉ có số trang + text), thứ tự trang quan trọng (phải giữ đúng thứ tự 1, 2, 3... để chunk và insert DB đúng thứ tự). `list[tuple]` là cấu trúc đơn giản nhất thể hiện đúng ý đó — không cần tạo 1 class/dataclass riêng cho 2 trường dữ liệu đơn giản (tránh over-engineering, giống nguyên tắc đã áp dụng nhiều lần trước đây trong dự án: không tạo abstraction khi chưa thật sự cần).
