## 3.10 — `GET /api/documents/{id}/status`

**File:** [`app/routers/documents.py`](../../app/routers/documents.py), [`app/schemas/document.py`](../../app/schemas/document.py)

### Code

```python
# schemas/document.py
class DocumentStatusResponse(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    status: str
    error_message: str | None
    page_count: int | None
```

```python
# routers/documents.py
@router.get("/{document_id}/status", response_model=DocumentStatusResponse)
async def get_document_status(
    document_id: uuid.UUID,
    current_user: User = Depends(get_current_user),
    db: AsyncSession = Depends(get_db),
):
    try:
        return await get_owned_document(db, document_id, current_user.id)
    except DocumentNotFoundError:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail={"code": "DOCUMENT_NOT_FOUND", "message": "Document not found"},
        )
```

### Nó làm gì (ý nghĩa)

Endpoint nhẹ để client (frontend) gọi lặp lại nhiều lần (poll — hỏi thăm định kỳ) trong lúc chờ `run_ingestion` (3.8, chạy nền sau khi upload ở 3.9) xử lý xong, biết được tiến trình hiện tại (`pending`/`parsing`/`embedding`/`ready`/`failed`) mà không cần tải lại toàn bộ thông tin document.

### Tại sao code theo cách này

1. **Vì sao có `DocumentStatusResponse` riêng, không dùng lại `DocumentResponse` sẵn có?** — `DocumentResponse` có nhiều field hơn mức cần (`filename`, `file_type`, `created_at`...) — endpoint này được gọi lặp lại rất nhiều lần trong lúc poll, trả về đúng 3 field cần thiết (`status`, `error_message`, `page_count`) giúp response nhẹ hơn, đúng tinh thần "nhẹ để poll" đã ghi trong kế hoạch.

2. **Vì sao tái sử dụng `get_owned_document` giống hệt `GET /{document_id}` thay vì viết query riêng?** — cùng 1 yêu cầu nghiệp vụ (lấy document, xác nhận đúng chủ sở hữu, báo 404 nếu không tìm thấy hoặc không phải của user) — không có lý do viết lại, và đảm bảo hành vi 404 nhất quán giữa các endpoint.

3. **Vì sao không lo việc `/{document_id}` (route đã có ở 3.2) và `/{document_id}/status` (route mới) bị nhầm lẫn thứ tự?** — 2 route có cấu trúc path khác nhau (1 segment vs 2 segment) nên framework tự phân biệt được chính xác, không phụ thuộc vào thứ tự khai báo.

### Test đã chạy (bằng chứng thật)

Test qua HTTP thật (`httpx.AsyncClient` + `ASGITransport`), đăng ký user thật, upload `b1-test.pdf` (mode `pypdf`), rồi gọi `GET /status` lặp lại:

- Poll ra đúng `{"status": "ready", "error_message": None, "page_count": 8}` sau khi ingestion chạy xong (mode `pypdf` chạy rất nhanh, không đủ thời gian bắt được các trạng thái trung gian `parsing`/`embedding` trong test này — nhưng đã xác nhận các trạng thái này hoạt động đúng khi test trực tiếp `run_ingestion` ở 3.8).
- Gọi với `document_id` ngẫu nhiên (không tồn tại) → `404 DOCUMENT_NOT_FOUND`.
- Gọi không kèm token xác thực → `401`.

### Bước này kết nối với các bước sau như thế nào

- Đây là endpoint cuối cùng cần cho luồng ingestion end-to-end hoàn chỉnh — **3.11** (test lỗi) và **3.12** (test e2e đủ 3 mode) sẽ dùng chính endpoint này để xác nhận trạng thái từ phía client, thay vì query DB trực tiếp như các bước trước.
