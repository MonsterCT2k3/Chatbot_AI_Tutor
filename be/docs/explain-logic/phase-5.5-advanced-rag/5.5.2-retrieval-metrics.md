## 5.5.2 — Retrieval metrics: Recall@k, MRR

**File:** [`app/evaluation/golden_dataset.py`](../../../app/evaluation/golden_dataset.py), [`app/evaluation/eval_documents.py`](../../../app/evaluation/eval_documents.py), [`app/evaluation/retrieval_metrics.py`](../../../app/evaluation/retrieval_metrics.py), [`app/evaluation/run_retrieval_eval.py`](../../../app/evaluation/run_retrieval_eval.py)

### Code

```python
# retrieval_metrics.py
@dataclass
class RetrievalResult:
    question: GoldenQuestion
    retrieved_pages: list[int]
    hit: bool
    rank: int | None  # 1-indexed rank of the first expected page found, None if not found


async def evaluate_question(
    db: AsyncSession, document_id: uuid.UUID, question: GoldenQuestion, k: int
) -> RetrievalResult:
    query_embedding = (await embed_chunks([question.question]))[0]
    chunks = await similarity_search(db, document_id, query_embedding, k=k)
    retrieved_pages = [chunk.page_number for chunk in chunks]

    rank = None
    for position, page in enumerate(retrieved_pages, start=1):
        if page in question.expected_pages:
            rank = position
            break

    return RetrievalResult(question=question, retrieved_pages=retrieved_pages, hit=rank is not None, rank=rank)


def recall_at_k(results: list[RetrievalResult]) -> float:
    if not results:
        return 0.0
    return sum(1 for r in results if r.hit) / len(results)


def mean_reciprocal_rank(results: list[RetrievalResult]) -> float:
    if not results:
        return 0.0
    return sum((1 / r.rank) if r.rank else 0.0 for r in results) / len(results)
```

### Nó làm gì (ý nghĩa)

Chạy toàn bộ 79 câu hỏi ở golden test set (5.5.1) qua đúng `similarity_search` thật (Phase 5.1) đang chạy trong production, đo 2 con số khách quan:
- **`Recall@k`**: trong số 79 câu hỏi, bao nhiêu % có ít nhất 1 trang đúng (`expected_pages`) xuất hiện trong top-`k` chunk trả về?
- **`MRR` (Mean Reciprocal Rank)**: trung bình của `1/rank`, với `rank` là vị trí (1, 2, 3...) mà trang đúng ĐẦU TIÊN xuất hiện trong danh sách kết quả — nếu trang đúng luôn xếp hạng #1, `MRR = 1.0` (điểm tối đa); càng xếp sau, điểm càng giảm.

Đây là con số **baseline** — mốc để so sánh khi làm hybrid search (5.5.4), reranking (5.5.5), query transformation (5.5.6) sau này: kỹ thuật nào không làm tăng con số này so với baseline thì không đáng để giữ lại.

### Luồng chạy chi tiết

Lấy đúng ví dụ thật đã chạy: câu hỏi `"Vòng lặp ReAct gồm 3 bước nào theo đúng thứ tự?"` (thuộc `b3-test.pdf`, `expected_pages=[2, 10]`).

1. **`ensure_eval_documents(db)`** (chạy 1 lần, TRƯỚC vòng lặp câu hỏi) — với mỗi file `app/data/slide-test/*.pdf`, kiểm tra xem user đánh giá (`EVAL_USER_ID`, 1 user cố định dùng riêng cho việc test) đã có sẵn document `status='ready'` cùng tên chưa. Nếu chưa, upload + `run_ingestion` thật (mode `pypdf`) rồi mới tiếp tục — lần chạy đầu tiên đã ingest thật cả 5 file (`b3-test.pdf` ra 10 chunk thật). Trả về `{"b3-test.pdf": <uuid thật>, ...}`.
2. **`load_golden_dataset()`** (5.5.1) — đọc cả 5 file JSON, trả về 1 list phẳng 79 `GoldenQuestion`, trong đó có đúng câu hỏi ví dụ trên.
3. **Với câu hỏi ví dụ, vào `evaluate_question`:**
   - `embed_chunks([question.question])` — gọi OpenAI embeddings thật, lấy vector 1536 chiều của câu hỏi.
   - `similarity_search(db, document_id, query_embedding, k=6)` (5.1) — trả về đúng 6 chunk liên quan nhất của `b3-test.pdf`, đã sắp theo độ liên quan.
   - `retrieved_pages = [chunk.page_number for chunk in chunks]` — với ví dụ này, kết quả THẬT là `[10, 2, 1, 8, 6, 3]` (trang 10 xếp #1!).
   - Vòng `for position, page in enumerate(retrieved_pages, start=1)`: `position=1, page=10` → `10 in [2, 10]` → ĐÚNG → `rank = 1`, dừng vòng lặp ngay (không cần xét tiếp).
   - Trả về `RetrievalResult(hit=True, rank=1, retrieved_pages=[10, 2, 1, 8, 6, 3])`.
4. **Lặp lại bước 3 cho cả 79 câu hỏi**, mỗi câu MỞ 1 SESSION DB RIÊNG (điểm mấu chốt — xem phần "Bug thật đã gặp" bên dưới).
5. **`recall_at_k(results)`** — đếm số `RetrievalResult` có `hit=True` chia cho tổng số 79 → `1.000` (mọi câu đều tìm thấy trang đúng trong top-6).
6. **`mean_reciprocal_rank(results)`** — với câu ví dụ trên, đóng góp `1/1 = 1.0` vào tổng; với 1 câu khác có trang đúng xếp hạng #3, đóng góp `1/3 ≈ 0.33`; lấy trung bình cả 79 câu → `0.914`.
7. **Ghi snapshot** — lưu toàn bộ chi tiết (từng câu hỏi, `retrieved_pages`, `hit`, `rank`) ra `app/evaluation/results/phase-5-baseline.json`, kèm `label` và `timestamp` — để 5.5.4 trở đi có thể load lại và so sánh số cũ/mới cạnh nhau.

### Bug thật đã gặp (quan trọng — đáng nhớ)

**Lần chạy đầu tiên ra kết quả rất tệ:** `Recall@6 = 0.329`, với RẤT NHIỀU câu hỏi có `retrieved_pages = []` (rỗng hoàn toàn) — kể cả với những document chắc chắn có dữ liệu (10-16 chunk/tài liệu, đã verify trực tiếp bằng SQL). Ban đầu nhìn giống như retrieval quality kém, nhưng con số rỗng bất thường (không phải "trang sai", mà là "KHÔNG CÓ chunk nào cả") là dấu hiệu của lỗi hệ thống, không phải lỗi chất lượng.

**Cách xác minh:** gọi TRỰC TIẾP `similarity_search` với đúng `document_id` + đúng câu hỏi vừa bị báo rỗng, TÁCH RIÊNG khỏi vòng lặp eval — kết quả trả về ĐÚNG 6 chunk, trang 10 xếp hạng #1. Điều này chứng minh dữ liệu và `similarity_search` hoàn toàn không có vấn đề gì — lỗi nằm ở CÁCH vòng lặp eval gọi nó.

**Nguyên nhân:** code gốc mở **1 session DB DÙNG CHUNG** cho suốt cả vòng lặp 79 câu hỏi (`async with async_session() as db:` bọc NGOÀI vòng `for`), khác hẳn pattern đã dùng NHẤT QUÁN xuyên suốt dự án (mỗi thao tác DB mở 1 session riêng — đúng như cách FastAPI's `get_db` cấp 1 session/request, và đúng như mọi script test trước đó trong dự án). Với 79 lượt gọi API embedding xen kẽ 79 truy vấn DB trải dài trên 1 session/transaction duy nhất (mỗi lượt đợi API thật mất cả giây), kết nối tới Supabase (qua pgbouncer transaction-mode pooler) có dấu hiệu bị ảnh hưởng, khiến 1 số truy vấn âm thầm trả về rỗng thay vì báo lỗi rõ ràng.

**Cách sửa:** đổi vị trí `async with async_session() as db:` vào TRONG vòng lặp — mỗi câu hỏi tự mở 1 session mới, dùng xong đóng ngay. Sau khi sửa: `Recall@6 = 1.000`, `MRR = 0.914` — khớp hoàn toàn với kết quả gọi trực tiếp lúc debug.

**Bài học:** 1 session DB sống quá lâu, xen kẽ nhiều lần `await` chờ API ngoài (embedding), là rủi ro thật — không chỉ là vấn đề "style code" mà có thể gây lỗi dữ liệu SAI mà KHÔNG hề có exception nào được raise ra để phát hiện. Số liệu "trông có vẻ hợp lý nhưng tệ" (như `Recall@6=0.329`) luôn đáng nghi ngờ và cần verify chéo bằng cách gọi tách biệt, không nên vội tin và kết luận "retrieval quality kém" ngay.

### Tại sao code theo cách này (các quyết định khác)

1. **Vì sao dùng `k=6` cho eval, khớp đúng default của `similarity_search` trong production, thay vì dùng `k` lớn hơn để "dễ đạt Recall cao hơn"?** — mục đích của eval là đo ĐÚNG những gì `ask()` (5.3) THẬT SỰ nhìn thấy trong production — nếu dùng `k` khác, con số đo được không phản ánh đúng trải nghiệm người dùng thật.
2. **Vì sao `EVAL_USER_ID` là 1 UUID cố định thay vì tạo user mới mỗi lần chạy?** — script này sẽ được CHẠY LẠI NHIỀU LẦN (baseline, rồi sau mỗi cải tiến ở 5.5.4-5.5.6) — dùng 1 user cố định + `ensure_eval_documents` kiểm tra "đã có sẵn chưa" giúp CHỈ ingest 1 lần duy nhất, các lần chạy sau tái sử dụng luôn, tiết kiệm thời gian + chi phí API đáng kể.
3. **Vì sao lưu kết quả ra file JSON (`results/{label}.json`) thay vì chỉ in ra màn hình?** — đúng tinh thần "đo trước, tối ưu sau": cần có bằng chứng LƯU LẠI được, so sánh cạnh nhau giữa các lần chạy (`phase-5-baseline.json` vs `phase-5.5-hybrid-search.json` sau này...), không thể chỉ dựa vào trí nhớ hay log console đã trôi qua.
4. **Vì sao báo cáo riêng danh sách "Misses" (câu hỏi bị trượt) thay vì chỉ in 2 con số tổng?** — 2 con số tổng hợp không cho biết CỤ THỂ câu hỏi nào đang có vấn đề — danh sách chi tiết giúp debug nhanh (như đã dùng chính danh sách này để phát hiện bug ở trên) và sau này giúp phân tích XEM LOẠI câu hỏi nào (VD câu hỏi về thông tin phụ ở footer/trang nhỏ) hay bị retrieval bỏ sót.

### Bước này kết nối với các bước sau như thế nào

- **5.5.3 (Answer-quality metrics)** sẽ tái sử dụng chính `document_ids` từ `ensure_eval_documents` và `questions` từ `load_golden_dataset`, chạy thêm `ask()` (5.3) thật cho từng câu, chấm điểm faithfulness/relevance.
- **5.5.4-5.5.6** (hybrid search, reranking, query transformation) mỗi kỹ thuật xong sẽ chạy lại đúng script này với `label` khác (VD `phase-5.5-hybrid-search`), so sánh trực tiếp với `phase-5-baseline.json` đã lưu ở đây — với baseline đã là `Recall@6=1.000`, các kỹ thuật sau khó có thể cải thiện thêm Recall (đã kịch trần) nhưng có thể vẫn cải thiện được `MRR` (đẩy trang đúng lên hạng cao hơn) hoặc cải thiện trên bộ câu hỏi khó hơn/đa dạng hơn sau này.
