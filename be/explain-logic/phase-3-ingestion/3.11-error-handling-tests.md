## 3.11 — Test xử lý lỗi

**Không có code mới** — bước này chỉ test (kiểm chứng) lại cơ chế `try/except` + rollback + `status='failed'` đã xây ở [3.8](3.8-run-ingestion.md), với các tình huống lỗi thật khác nhau (chưa test ở 3.8: file rỗng, file hỏng nội dung, API key sai).

### Mục tiêu

Xác nhận: dù lỗi xảy ra ở giai đoạn nào (đọc file, convert PPTX, gọi API ngoài), `run_ingestion` luôn kết thúc gọn gàng với `status='failed'` + `error_message` rõ ràng — **không bao giờ crash không kiểm soát, không bao giờ để document kẹt mãi ở `pending`/`parsing`/`embedding`.**

### Các case đã test (bằng chứng thật)

| Case | Cách tạo lỗi | Kết quả |
|---|---|---|
| File PDF rỗng (0 byte) | Upload `file_bytes=b""` | `status='failed'`, `error_message="Cannot read an empty file"` (lỗi từ `pypdf`) |
| File PDF nội dung hỏng | Upload bytes text thường (`b"this is definitely not a valid pdf..."`), đặt tên `.pdf` | `status='failed'`, `error_message="Stream has ended unexpectedly"` (lỗi từ `pypdf`) |
| File PPTX hỏng | Upload bytes rác, đặt tên `.pptx` | `status='failed'`, `error_message="Error: source file could not be loaded"` (lỗi từ LibreOffice, bắt qua `PptxConversionError`) |
| `MISTRAL_API_KEY` sai (mode `mistral_ocr`) | Tạm thay `_mistral_client` bằng client key giả trong lúc test | `status='failed'`, `error_message='API error occurred: Status 401. Body: {"detail":"Invalid API Key"}'` |

Cả 4 case đều đi qua đúng nhánh `except Exception as e` đã thiết kế ở 3.8: `rollback()` → lấy lại `document` sạch → ghi `status='failed'` + `error_message` → `commit()`. Không có page/chunk rác nào bị tạo ra trong mọi case.

### Phát hiện phụ (chưa xử lý, ghi lại để nhớ)

**Case API key sai mất ~40 giây mới báo lỗi**, thay vì báo ngay lập tức. Nguyên nhân: `_retry_async` (xây ở 3.2) coi MỌI exception là đáng thử lại (retry), kể cả lỗi vĩnh viễn như `401 Unauthorized` (sai key thì thử lại bao nhiêu lần cũng vẫn sai, không giống lỗi mạng tạm thời sẽ tự hết sau vài giây). Với `max_retries=5`, `backoff_factor=2`, tổng thời gian chờ giữa các lần thử là `2+4+8+16=30` giây trước khi thử lần cuối và raise lỗi thật.

- **Ảnh hưởng thực tế:** không sai kết quả cuối cùng (vẫn ra `status='failed'` đúng), chỉ là chậm hơn cần thiết — người dùng phải đợi lâu hơn để thấy lỗi rõ ràng khi cấu hình sai (thường chỉ xảy ra lúc setup ban đầu, không phải lỗi thường gặp khi vận hành).
- **Hướng cải thiện (chưa làm)**: phân biệt lỗi nên retry (lỗi mạng, timeout, HTTP 5xx — server tạm thời quá tải) và lỗi không nên retry (HTTP 401/403 — sai quyền truy cập, thử lại vô ích) trong `_retry_async`, ví dụ kiểm tra mã lỗi HTTP nếu exception có sẵn thông tin đó.
- **Vì sao không sửa ngay trong bước này**: 3.11 là bước TEST, không phải bước sửa code — phát hiện được ghi lại để làm ở 1 bước cải thiện riêng sau này (không cấp bách, vì `MISTRAL_API_KEY` sai chỉ xảy ra lúc cấu hình môi trường, hiếm khi xảy ra lúc vận hành thật).

### Bước này kết nối với các bước sau như thế nào

- **3.12** (test end-to-end đủ 3 mode) sẽ tập trung vào các case THÀNH CÔNG (happy path) qua HTTP thật — bổ sung cho bước này vốn tập trung vào các case LỖI.
