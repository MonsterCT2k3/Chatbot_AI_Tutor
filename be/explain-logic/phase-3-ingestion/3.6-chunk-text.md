## 3.6 — `chunk_text`: cắt nhỏ text theo token, ưu tiên theo đoạn văn

**File:** [`app/services/ingestion_service.py`](../../app/services/ingestion_service.py)

> Bước này đã có **đặc tả chi tiết viết trước khi code** tại [`development-plan/specification-for-phase-3/3.6-chunk-text.md`](../../development-plan/specification-for-phase-3/3.6-chunk-text.md) — file đó mô tả thuật toán, edge case, kế hoạch test. File này (explain-logic) tập trung vào: code thật đã viết ra sao, và **kết quả test thật** so với dự tính trong spec.

### Code

```python
_PARAGRAPH_SPLIT_RE = re.compile(r"\n\s*\n+")
_SENTENCE_SPLIT_RE = re.compile(r"(?<=[.!?])\s+")


def _greedy_group(parts: list[str], encoding: tiktoken.Encoding, max_tokens: int, joiner: str) -> list[str]:
    chunks: list[str] = []
    current_parts: list[str] = []
    current_tokens = 0

    for part in parts:
        part_tokens = len(encoding.encode(part))
        if current_parts and current_tokens + part_tokens > max_tokens:
            chunks.append(joiner.join(current_parts))
            current_parts = []
            current_tokens = 0
        current_parts.append(part)
        current_tokens += part_tokens

    if current_parts:
        chunks.append(joiner.join(current_parts))
    return chunks


def chunk_text(text: str, max_tokens: int = 300) -> list[str]:
    text = text.strip()
    if not text:
        return []

    encoding = tiktoken.encoding_for_model("text-embedding-3-small")
    paragraphs = [p.strip() for p in _PARAGRAPH_SPLIT_RE.split(text) if p.strip()]

    chunks: list[str] = []
    current_parts: list[str] = []
    current_tokens = 0

    for paragraph in paragraphs:
        paragraph_tokens = len(encoding.encode(paragraph))

        if paragraph_tokens > max_tokens:
            if current_parts:
                chunks.append("\n\n".join(current_parts))
                current_parts = []
                current_tokens = 0

            sentences = [s.strip() for s in _SENTENCE_SPLIT_RE.split(paragraph) if s.strip()]
            chunks.extend(_greedy_group(sentences, encoding, max_tokens, " "))
            continue

        if current_parts and current_tokens + paragraph_tokens > max_tokens:
            chunks.append("\n\n".join(current_parts))
            current_parts = []
            current_tokens = 0

        current_parts.append(paragraph)
        current_tokens += paragraph_tokens

    if current_parts:
        chunks.append("\n\n".join(current_parts))

    return chunks
```

### Nó làm gì (ý nghĩa)

Nhận vào text của 1 trang, trả về danh sách các **chunk** (đoạn nhỏ hơn, mỗi đoạn ≤ `max_tokens`, mặc định 300 token). Đây là bước bắt buộc trước khi embed (3.7) — không thể embed nguyên 1 trang dài làm 1 vector duy nhất, vì như vậy khi tìm kiếm sẽ không đủ chính xác (1 trang có thể nói về nhiều ý khác nhau, gộp chung làm loãng ý nghĩa vector).

### Tại sao code theo cách này (giải thích từng quyết định)

Hầu hết các quyết định thiết kế (vì sao ưu tiên đoạn văn trước câu, vì sao không overlap, vì sao không cắt cứng giữa từ...) đã giải thích kỹ trong **đặc tả** — không lặp lại ở đây. Chỉ nêu thêm vài điểm phát sinh lúc code thật:

1. **Vì sao tách hàm `_greedy_group` riêng thay vì viết logic gom-và-chốt (accumulate-and-flush) trực tiếp trong `chunk_text`?**
   Logic "gom từng phần tử vào 1 chunk đang xây, hễ vượt giới hạn thì chốt lại và bắt đầu chunk mới" cần dùng **2 lần**: 1 lần cho đoạn văn (paragraph), 1 lần cho câu (sentence) khi 1 đoạn văn quá dài. Tách thành hàm riêng `_greedy_group(parts, encoding, max_tokens, joiner)` để không viết trùng cùng 1 đoạn logic 2 lần — tham số `joiner` cho phép dùng lại y hệt logic nhưng nối bằng `"\n\n"` (khi gom đoạn văn) hay `" "` (khi gom câu).

2. **Vì sao 2 regex khác nhau cho tách đoạn (`_PARAGRAPH_SPLIT_RE`) và tách câu (`_SENTENCE_SPLIT_RE`)?**
   - Tách đoạn: `r"\n\s*\n+"` — tìm 1 dòng trống trở lên (1 hoặc nhiều `\n`, có thể xen khoảng trắng). Ứng phó được cả trường hợp nhiều dòng trống liên tiếp bất thường (đã liệt kê trong bảng edge case của đặc tả).
   - Tách câu: `r"(?<=[.!?])\s+"` — tách sau dấu `.`/`!`/`?` và khoảng trắng theo sau. Đây là cách tách câu đơn giản (heuristic — quy tắc kinh nghiệm, không phải NLP thật sự hiểu ngữ nghĩa), có nhược điểm đã biết trước: không phân biệt được dấu chấm trong từ viết tắt (VD "TS." — Tiến sĩ) với dấu chấm kết câu thật. Chấp nhận được vì đây là fallback hiếm khi dùng tới (chỉ kích hoạt khi 1 đoạn văn tự nó đã vượt 300 token), không đáng để dùng thư viện NLP tách câu phức tạp hơn cho 1 trường hợp hiếm.

### Test đã chạy (bằng chứng thật, so với kế hoạch trong đặc tả)

Đã chạy đủ cả 5 mục trong kế hoạch test của đặc tả:

1. ✅ Text rỗng/chỉ khoảng trắng → `[]`.
2. ✅ Text ngắn (1 câu) → đúng 1 chunk, giữ nguyên nội dung.
3. ✅ Text dài tổng hợp (20 đoạn văn lặp lại) chia với `max_tokens=100` → 100 chunk, **0 chunk vượt giới hạn** (đo bằng `tiktoken` thật, không đoán), ghép lại đủ **100% số từ gốc**, không mất/lặp.
4. ✅ Text thật từ `pypdf` (10 trang `b3-test.pdf`) → mỗi trang ra đúng 1 chunk (vì trang ngắn), không chunk nào vượt 300 token.
5. ✅ **Test quan trọng nhất** — text thật từ `mistral_ocr` cho trang có mô tả sơ đồ dài (trang 9, "Tool Calling", 934 token) → chia thành **5 chunk, đều dưới 300 token**. Đáng chú ý: ranh giới chunk sinh ra **trùng khớp tự nhiên** với các mục trong prompt đã thiết kế ở [3.2](3.2-describe-image-pixtral.md) (chunk 3 ≈ đúng mục "Số liệu & Insight quan trọng", chunk 4 ≈ đúng mục "Ý nghĩa bài học") — xác nhận thuật toán chung (không cần biết mode nào sinh ra text) đã tận dụng đúng cấu trúc markdown có sẵn trong output của Mistral, đúng như dự đoán khi bàn luận trước khi code (xem lịch sử trò chuyện: quyết định dùng 1 hàm chung cho cả 3 mode, không viết riêng từng mode).
