# Đặc tả kỹ thuật — 3.8 `run_ingestion`

> Bước này phức tạp hơn hẳn 3.1-3.7 (orchestrate — điều phối toàn bộ 7 bước đã làm, cộng thêm R2 + DB + status transitions), nên viết spec trước khi code, khác với 3.7 (đã đồng ý bỏ spec cho bước đơn giản).

## 1. Mục tiêu

Nhận vào `document_id` (1 document đã có sẵn record `status='pending'` từ Phase 2), chạy toàn bộ pipeline: tải file → convert (nếu PPTX) → trích xuất text → chunk → embed → lưu hết vào DB → cập nhật `status` đúng theo từng giai đoạn, hoặc `status='failed'` nếu có lỗi ở bất kỳ đâu.

## 2. Vị trí file + chữ ký hàm

- **File mới**: `app/workers/ingestion_worker.py` (hiện đang là file rỗng/comment placeholder).
- **Chữ ký hàm**: `async def run_ingestion(document_id: uuid.UUID) -> None`
- Hàm này **tự mở session DB riêng** (`async_session()`), không nhận `db` từ bên ngoài — vì hàm chạy như 1 background task (`background_tasks.add_task`, nối ở bước 3.9), tại thời điểm chạy thì request HTTP gốc đã trả response xong, session của request đó đã đóng — bắt buộc phải tự mở session mới.

## 3. Việc cần làm thêm trước khi code (phát hiện lúc lập spec, không phải lúc code)

**`storage_service.py` hiện chưa có hàm tải file XUỐNG** — chỉ có `upload_file`, `get_presigned_url`, `delete_file`. Cần thêm:

```python
async def download_file(key: str) -> bytes:
    response = await run_in_threadpool(_client.get_object, Bucket=settings.R2_BUCKET_NAME, Key=key)
    return await run_in_threadpool(response["Body"].read)
```

(Cùng lý do `run_in_threadpool` như `upload_file`/`delete_file` đã có — `boto3` là thư viện blocking.)

## 4. Luồng xử lý chi tiết (step-by-step)

```
1. Mở session DB mới, lấy Document theo document_id.
   - Nếu không tồn tại (đã bị xoá?) → return sớm, không làm gì (defensive — phòng thủ,
     không nên xảy ra thật nhưng không nên crash nếu xảy ra).

2. try:
   a. status = 'parsing' → commit ngay (để GET /status ở bước 3.10 thấy được
      trạng thái thật, không phải chỉ có trong bộ nhớ).

   b. Tải file gốc từ R2: file_bytes = await download_file(document.storage_key)

   c. Nếu document.file_type == 'pptx':
        pdf_bytes = await convert_pptx_to_pdf(file_bytes)          # bước 3.5
        converted_key = f"documents/{document.user_id}/{document.id}/converted.pdf"
        await upload_file(pdf_bytes, converted_key, content_type="application/pdf")
        document.converted_pdf_key = converted_key
        await commit
      Ngược lại (đã là PDF):
        pdf_bytes = file_bytes

   d. extraction_mode = document.metadata_.get("extraction_mode", "pypdf")

   e. Nếu extraction_mode cần OCR (mistral_ocr HOẶC hybrid):
        pdf_key = document.converted_pdf_key or document.storage_key
        document_url = get_presigned_url(pdf_key, expires_in=3600)

   f. Trích xuất text theo mode:
        "pypdf"       → extract_text_pypdf(pdf_bytes)                       # sync, 3.1
        "mistral_ocr" → await extract_text_mistral_ocr(document_url)        # 3.3
        "hybrid"      → await extract_text_hybrid(pdf_bytes, document_url)  # 3.4
        (mode lạ không nhận diện được → coi như lỗi thật, rơi vào except bên dưới,
         KHÔNG âm thầm fallback về pypdf — fail rõ ràng tốt hơn xử lý sai âm thầm)

   g. Với mỗi (page_number, text) trong kết quả bước f:
        tạo DocumentPage(document_id=.., page_number=.., raw_text=text)
        add vào session, flush() để lấy được page.id ngay (cần cho bước i,
        document_chunks.page_id là NOT NULL, phải có trước khi insert chunk)
      commit sau khi thêm hết các trang.

   h. status = 'embedding' → commit.

   i. Với mỗi (page_number, text) đã có ở bước g:
        chunks = chunk_text(text)                    # 3.6, có thể trả về []
        nếu chunks rỗng → bỏ qua trang này (trang trắng, không có gì để embed)
        gom (page_number, chunk_index, content) vào 1 list DÙNG CHUNG cho
        TOÀN BỘ document (không phải list riêng từng trang)

      Sau khi duyệt hết mọi trang:
        nếu list gộp không rỗng:
          vectors = await embed_chunks([content cho từng phần tử])   # 3.7,
             GỌI 1 LẦN DUY NHẤT cho cả document, không phải 1 lần/trang —
             tận dụng đúng khả năng batch của embed_chunks, giảm số lần gọi
             API từ N (số trang) xuống còn 1.
          với mỗi (page_number, chunk_index, content), vector tương ứng:
             tạo DocumentChunk(document_id=.., page_id=page_id_by_number[page_number],
                                page_number=.., chunk_index=.., content=..,
                                embedding=vector)
             add vào session
        commit.

   j. status = 'ready', page_count = số trang đã xử lý → commit.

3. except Exception as e:
   await db.rollback()   # bỏ mọi thay đổi CHƯA commit trong bước đang dở
   document = await db.get(Document, document_id)   # lấy lại object SẠCH sau
                                                       # rollback, tránh dựa vào
                                                       # trạng thái không chắc chắn
                                                       # của object cũ trong bộ nhớ
   document.status = 'failed'
   document.error_message = str(e)[:2000]   # cắt bớt nếu quá dài, tránh lỗi
                                              # ghi DB nếu message dài bất thường
   await commit
```

## 5. Các quyết định thiết kế quan trọng (giải thích tại sao)

1. **Commit từng giai đoạn (incremental) thay vì 1 transaction lớn duy nhất cho cả hàm** — lý do: `status` phải phản ánh đúng tiến trình THẬT SỰ đã lưu trong DB tại từng thời điểm, để `GET /api/documents/{id}/status` (bước 3.10, cho phép poll liên tục trong lúc ingest) thấy được `parsing` → `embedding` → `ready` tuần tự thật, không phải chỉ thấy `pending` rồi nhảy thẳng lên `ready`/`failed` ở cuối cùng.

2. **Batch TOÀN BỘ chunk của document trong 1 lần gọi `embed_chunks`, không phải 1 lần/trang** — tận dụng đúng thiết kế "batch" đã có sẵn ở 3.7, giảm số lần gọi API embedding từ N (số trang) xuống 1 — nhanh hơn, rẻ hơn (ít overhead mạng hơn). **Giới hạn cần biết**: OpenAI embeddings API nhận tối đa khoảng 2048 phần tử/lần gọi — với tài liệu bài giảng thông thường (vài chục tới ~100 trang, mỗi trang vài chunk), tổng số chunk khó vượt qua giới hạn này. Nếu sau này gặp tài liệu cực lớn vượt ngưỡng, sẽ cần chia batch nhỏ hơn — chưa cần xử lý ngay vì chưa có bằng chứng sẽ gặp ở quy mô hiện tại (tránh over-engineering).

3. **Không âm thầm fallback về `pypdf` nếu `extraction_mode` không nhận diện được** — 1 giá trị mode lạ (VD lỗi nhập liệu, bug ở bước 3.9) nên **fail rõ ràng** (`status='failed'`, `error_message` nói rõ lý do) thay vì âm thầm dùng `pypdf` khiến người dùng không biết chọn mode của mình đã bị bỏ qua.

4. **`db.rollback()` + lấy lại `document` bằng `db.get()` MỚI trong khối `except`** — sau `rollback()`, SQLAlchemy đánh dấu các object trong session là "hết hạn" (expired), truy cập lại có thể phát sinh hành vi khó đoán. Lấy lại chắc chắn 1 object sạch, mới, đảm bảo ghi `status='failed'` luôn thành công dù lỗi xảy ra ở đâu trong luồng xử lý.

5. **`document.metadata_.get("extraction_mode", "pypdf")`** — dùng `.get()` với giá trị mặc định `"pypdf"` (không phải index trực tiếp `["extraction_mode"]`) — phòng trường hợp record cũ/test không có field này trong `metadata`, không nên crash vì thiếu 1 key JSON.

## 6. Trường hợp biên (Edge cases)

| Trường hợp | Xử lý |
|---|---|
| `document_id` không tồn tại trong DB | Return sớm, không làm gì, không raise lỗi ồn ào (đây là tình huống bất thường ở tầng gọi, không phải lỗi của `run_ingestion`). |
| File không tồn tại trên R2 (storage_key sai/đã bị xoá) | `download_file` sẽ raise lỗi từ `boto3` — rơi vào `except`, `status='failed'` với message rõ ràng. |
| PPTX convert lỗi (`PptxConversionError`, bước 3.5) | Rơi vào `except` chung, `status='failed'`. |
| 1 trang chunk ra `[]` (trang trắng) | Bỏ qua trang đó khi gom chunk, KHÔNG coi là lỗi — tài liệu vẫn `ready` bình thường, chỉ là trang đó không có chunk nào trong `document_chunks`. |
| Toàn bộ tài liệu không trích được chữ nào (mọi trang đều rỗng) | Vẫn set `status='ready'`, `page_count` đúng số trang, nhưng `document_chunks` rỗng hoàn toàn cho document đó — không coi là lỗi (đây là tài liệu thật sự không có nội dung text, không phải bug). |
| Mistral OCR/embedding API lỗi mạng tạm thời | Đã có `_retry_async` xử lý ở tầng 3.2/3.3/3.7 — nếu retry hết vẫn lỗi, lỗi đó nổi lên `run_ingestion`, rơi vào `except`, `status='failed'`. |

## 7. Kế hoạch test

**Chưa nối vào HTTP (đó là việc của 3.9)** — test bằng cách gọi `run_ingestion(document_id)` **trực tiếp** trong script test, với `document_id` của 1 record đã tồn tại thật trong DB (tạo thủ công qua `document_service.create_document` hoặc insert thẳng, dùng file thật từ `app/data/slide-test/`).

1. **Test happy path — mode `pypdf`**: tạo document PDF thật → chạy `run_ingestion` → verify bằng query SQL thật:
   - `status == 'ready'`, `page_count` đúng số trang.
   - Số row `document_pages` khớp số trang.
   - Số row `document_chunks` > 0, mọi `embedding` khác `NULL`.
2. **Test happy path — mode `mistral_ocr`** (dùng `b1-test.pdf`, rẻ hơn `b3-test.pdf` toàn ảnh): tương tự bước 1, thêm kiểm tra text trong `document_pages.raw_text` của trang có ảnh chứa mô tả thật (không phải tag placeholder).
3. **Test happy path — mode `hybrid`**: tương tự, kiểm tra thêm: trang không ảnh → `raw_text` giống hệt bản `pypdf` thuần.
4. **Test PPTX thật**: dùng file `.pptx` test tạo bằng `python-pptx` (như ở 3.5) → verify `converted_pdf_key` được set, trỏ tới object thật tồn tại trên R2.
5. **Test lỗi**: cố tình trỏ `document.storage_key` tới 1 key không tồn tại trên R2 → verify `status='failed'`, `error_message` không rỗng, không có `document_pages`/`document_chunks` rác nào được tạo ra (transaction của giai đoạn đang dở bị rollback đúng).
6. Dọn dẹp: xoá document/pages/chunks test đã tạo sau khi test xong (hoặc dựa vào `ON DELETE CASCADE` khi xoá `documents` row).

## 8. Kết nối với các bước sau

- **3.9** sẽ gọi `background_tasks.add_task(run_ingestion, document.id)` ngay sau khi `POST /api/documents` tạo xong record — không gọi trực tiếp (blocking) trong request, để response trả về ngay (202) trong khi ingest chạy nền.
- **3.10 (`GET /status`)** đọc trực tiếp `document.status`/`error_message`/`page_count` — chính là những field `run_ingestion` cập nhật ở từng bước.
